# 通用逆向方法论（拿到任何未知目标都适用）

## 1. 五个分析层次 —— 卡住就换层

```
L5 语义层  Semantic   → 它「想干什么」？业务意图是什么？
L4 代码层  Code       → 反编译/反汇编后的逻辑是什么？
L3 结构层  Structural → 文件格式、协议字段、数据结构长什么样？
L2 行为层  Behavioral → 输入输出、系统调用、网络行为是什么？
L1 表征层  Physical   → 它是 PE/ELF/Mach-O/DEX/字节码？什么架构？
```

**新手和老手的差别，就在于能不能在层次之间快速上下切换：**

- 死磕汇编看不懂 → **往上跳**：先跑起来看它干了什么（行为层），往往一眼就懂。
- 看懂行为但说不清机制 → **往下沉**：去代码层确认那个校验函数到底怎么算的。

## 2. 三类基本技术与一条铁律

| 类型 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| 静态分析 | 不运行，读文件/反汇编/反编译 | 安全、可离线、覆盖面全、可自动化 | 难解混淆与加密；看不到运行时状态 |
| 动态分析 | 运行起来，调试、插桩、观察 | 看到真实数据；加密必然在运行时解密；能验证假设 | 需要环境；可能被反调试/反虚拟机对抗 |
| 混合分析 | 静态定位 + 动态验证，来回迭代 | **事实上的最优解** | 复杂度最高 |

> **铁律：凡是加密、压缩、虚拟化保护的东西，静态一定看不全，必须在运行时截获。**
> 这是脱壳、抓解密前明文、绕过混淆的通用思想。

## 3. 假说驱动法（Hypothesis-Driven Analysis）

逆向工程师真正的工作方式，不是「从头到尾读反编译代码」：

```
观察现象 → 提出假说 → 设计实验 → 执行 → 结果支持/证伪 → 修正假说 → 循环
```

**举例：**

- 现象：`strings` 里看到 `https://api.xxx.com/v1/report`
- 假说：这个程序会向该地址上报数据
- 实验：Hook `SSL_write` / 用代理抓包 / 断网观察是否报错
- 结果：抓到了上报包 → 假说成立 → 下一层假说：上报内容里有设备指纹？

**差分实验（Differential Analysis）是最常用的武器：**

| 实验方式 | 能推断出什么 |
|---|---|
| 改输入的一个字节，看输出怎么变 | 哪个字节是长度 / 校验和 / 序号 |
| 对比两个版本（v1.0 vs v1.1）的二进制差异 | 本次更新改了什么逻辑（bindiff） |
| 对比两个不同内容的样本文件 | 哪些字节随内容变（数据段），哪些不变（结构段） |
| 对比加壳前后 / 开关某个功能前后 | 定位功能开关与关键分支 |

本技能包里 `re.py diff A B` 就是为差分实验准备的。

## 4. 通用 0→1 分析 SOP

```
Step 0  定目标与边界：我要回答什么问题？授权范围是什么？（见 legal.md）
Step 1  识别（Identification）
        re.py identify → 什么格式、什么架构、什么编译器、加没加壳
Step 2  指纹（Fingerprinting）
        re.py strings / imports → 快速建立「它是干什么的」的直觉
Step 3  静态全景（Static Survey）
        反编译/反汇编 → 找入口、找主流程、找关键函数、画调用关系
Step 4  行为观测（Behavioral Observation）
        沙箱 / 真机跑一遍 → 文件、注册表、网络、进程行为全记录
Step 5  定点突破（Targeted Attack）
        针对关键逻辑下断点 / Hook / 插桩 → 拿到真实运行时数据
Step 6  对抗处理（若需要）
        脱壳 / 反混淆 / 过反调试 → 得到可读形态
Step 7  建模与验证（Modeling & Validation）
        写出解析器 / 客户端 / 算法 → 跑通 = 完成
Step 8  文档化（Documentation）
        重命名、加注释、画 CFG/数据结构图、写报告（re.py report）
```

## 5. 唯一的验收标准：复现即理解

**能写出一个行为与原程序一致的实现（解析器 / 客户端 / 算法），就算真懂了。**

- 逆向协议 → 写出能跟真实服务端正常对话的客户端
- 逆向文件格式 → 写出能正确读取所有样本的解析器
- 逆向算法 → 写出输入相同则输出相同的代码

写不出来，说明还有隐藏分支没覆盖，回去继续。

## 6. 难度由两个变量决定

```
难度 ≈ f(元数据保留了多少, 控制流被破坏了多少)
```

- 保护技术全部围绕**破坏**这两点展开
- 逆向技术全部围绕**恢复**这两点展开

难度光谱（易 → 难）：

```
前端JS  .NET(JIT)  Java  Python  Android DEX  iOS ObjC  Go  WASM
                                                                ↓
                    NativeAOT .NET / C++ O2 / Rust release / VMP 虚拟机壳 / 加密固件
```

**先建立心理预期，再决定投入多少成本。**

## 7. 前置知识速查（看汇编必备）

### 调用约定（认错参数个数和位置，整个函数就分析错了）

| 约定 | 整数参数 | 浮点 | 栈 | 易错点 |
|---|---|---|---|---|
| x86 cdecl | 栈（右→左压） | 栈 | 调用方清栈 | 调用后有 `add esp, N` |
| x86 stdcall | 栈 | 栈 | **被调方**清栈 | 见到 `ret 8` 就是它 |
| x86 fastcall | ECX, EDX | — | 其余栈 | MSVC 与 Borland 不兼容 |
| x86 thiscall | ECX = `this` | — | 栈 | C++ 成员函数 |
| Microsoft x64 | RCX, RDX, R8, R9 | XMM0–3 | **32 字节 shadow space** | RDI/RSI 是被调保存 |
| System V AMD64 | RDI, RSI, RDX, RCX, R8, R9 | XMM0–7 | 无 shadow，有 red zone | 第 4 个参数开始与 MS 分叉 |
| ARM64 AAPCS | X0–X7 | V0–V7 | 16 字节对齐，X29=FP，X30=LR | X8=间接返回，X19–X28 被调保存 |

⚠️ shadow space 与 red zone 互斥；Windows 的经验不能直接套到 Linux ELF 上。

### 编译器优化对逆向的破坏

| 优化 | 逆向时的症状 |
|---|---|
| `-O0` | 栈帧完整、变量都在栈上，最易读 |
| `-O1/-O2` | 变量消失，值在寄存器间漂移 |
| `-fomit-frame-pointer` | 函数边界难定，回溯调用链困难 |
| 内联 | 一个「函数」里塞了三层逻辑 |
| 尾调用 | `call`+`ret` 变成 `jmp`，调用关系图错乱 |
| LTO | 符号大幅减少，静态库边界消失 |

### 符号与元数据的价值排序

1. **PDB / DWARF / dSYM** —— 带行号、类型、源码路径，等于半开源
2. **完整符号表**（`.symtab` / `LC_SYMTAB`）—— 有函数名的世界和没函数名的世界是两个游戏
3. **语言级元数据** —— .NET Metadata、Java 常量池、ObjC 类结构、Go `pclntab`、DEX `string_ids`
4. **异常处理表 / RTTI** —— 能推出函数边界与类层次
5. **字符串** —— 最低保底，但往往信息量惊人

## 8. 断点选型（会不会被检测）

| 类型 | 实现 | 数量 | 会被检测吗 |
|---|---|---|---|
| 软件断点 | 改写指令为 `INT3`(0xCC) | 无限 | **会**——代码完整性扫描可发现 |
| 硬件断点 | DR0–DR3 | 4 个 | **不改代码**，最隐蔽 |
| 内存断点 | PAGE_GUARD 触发异常 | 按页 | 可被 `VirtualQuery` 察觉 |
| 条件断点 | 调试器判定条件 | — | 慢，但好用 |

> **反反调试第一原则：用硬件断点代替软件断点。**

## 9. 常见反调试手段（认出来才能绕过）

| 手段 | Windows | Linux | macOS |
|---|---|---|---|
| 标志位 | PEB!BeingDebugged | `/proc/self/status` 的 TracerPid | `sysctl` 的 `P_TRACED` |
| API 查询 | `IsDebuggerPresent`、`NtQueryInformationProcess` | `ptrace(PTRACE_TRACEME)` 自检 | — |
| 堆标志 | PEB!NtGlobalFlag、Heap Flags | — | — |
| 提前执行 | **TLS Callback**（main 之前） | `.init_array` / `__attribute__((constructor))` | `+load` / `__mod_init_func` |
| 时间差 | `RDTSC` / `QueryPerformanceCounter` | `clock_gettime` | `mach_absolute_time` |
| 环境检测 | 进程名/窗口名/父进程异常 | — | — |

> ⚠️ PEB 的具体偏移（`fs:[0x30]+0x2` 等）随 Windows 版本与 Wow64 变化，
> 精确值以当前系统 `dt _PEB` 为准，不要照抄博客上的数字当结论。

## 10. 反混淆思路

| 混淆手段 | 特征 | 还原思路 |
|---|---|---|
| 控制流平坦化 CFF | 大 dispatcher + 状态变量 + 无数 switch | 符号执行追踪状态变量，映射回原基本块重建 CFG |
| 不透明谓词 | 恒真/恒假判断（如 `(x*(x-1))%2==0`） | Z3 判可达性，NOP 掉不可达分支 |
| 指令替换 MBA | `x+y` 写成 `(x^y)+2*(x&y)` | MBA 求解器 / arybo / Z3 化简 |
| 虚假控制流 | 插入永不执行的分支 | 同上 |
| 字符串加密 | 运行时才解密 | Hook 解密函数 / Unicorn 模拟执行解密例程 |
