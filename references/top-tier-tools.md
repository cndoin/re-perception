# 顶尖逆向工程师的工具、套路与「AI 可达性」对照表

> 本文回答三个问题：
> 1. 顶尖逆向工程师（IDA/Ghidra/BN 用户、恶意软件分析师、CTF 选手）**实际怎么干**？
> 2. 他们用的工具**核心竞争力（"神特点"）到底是什么**？
> 3. 这些能力**哪些能用零依赖 Python 复现 / 从开源搬 / 必须外挂**？
>
> 结论会直接变成 `scripts/` 里的实现（见文末「落地路线」）。
> 调研时间：2026-09；来源见文末「参考」。

## 一、三段式工作流：真实的高手是这么走的

几乎所有顶尖分析师的流程都可以压成三段。**注意顺序：先省事，再省力，最后才硬啃。**

### 第 1 段：省事层 —— 「能不能不逆？」

逆向最大的浪费，是把别人已经开源、能拿到源码的代码又逆了一遍。

| 动作 | 用什么 | 一句话理由 |
|---|---|---|
| 成分识别 | 字符串里的版本号/路径、导入表、语言指纹 | 命中开源组件 → 直接看源码，不用逆 |
| 符号恢复 | Go `pclntab`、Rust panic 路径、.NET 元数据、Java 常量池、ObjC | **一条命令就能拿到成千上万个真名**，这是投入产出比最高的 5 分钟 |
| 版本比对 | BinDiff / Diaphora / Ghidra Version Tracking | 有旧版就把名字/注释/结构体**移植**过来，「重新命名」是最耗时的劳动 |
| 编译器指纹 | Rich 头、FLIRT/库签名、`/GL`、`-O2` 痕迹 | 认出编译器 = 预判代码长相，知道 CRT 在哪、怎么优化 |

### 第 2 段：省力层 —— 把重复劳动自动化

| 动作 | 用什么 | 关键点 |
|---|---|---|
| 静态打点 | 导入表、交叉引用、字符串↔代码的 xref | 高手**不从 main 顺序往下读**，而是从字符串/可疑 API 反向扩散 |
| 结构识别 | CFG、循环、switch 跳转表 | 先认结构再读指令，比逐条读快一个量级 |
| 库函数剥离 | FLIRT 签名匹配 | 把 CRT/OpenSSL/zlib 全部标灰，剩下的才是用户代码 |
| 混淆还原 | 栈字符串、XOR 串、API 哈希 | 静态看不见的必须**模拟执行**或上动态 |

### 第 3 段：硬啃层 —— 只能人肉的部分

| 动作 | 用什么 | 现实 |
|---|---|---|
| 反编译阅读 | Hex-Rays > Ghidra > BN HLIL > r2 pdc | 反编译**永远 80% 对 20% 错**，可疑处必须回汇编 |
| 动态验证 | x64dbg / WinDbg / Frida | 加密/压缩的东西静态一定看不全，**必须在运行时截获** |
| 差分定位 | 补丁比对（CVE 出来后 diff 前后版本） | 找漏洞最快路径不是读代码，是看补丁改了哪几行 |
| 重写验证 | 写出等价解析器/协议客户端 | **逆向的验收标准是复现**，不是「看起来懂了」 |

## 二、工具矩阵与「神特点」拆解

### 2.1 反汇编/反编译平台

| 工具 | 神特点 | 可迁移到我们这吗 |
|---|---|---|
| **IDA Pro + Hex-Rays** | ① **FLIRT 库签名**（静态链接函数识别的事实标准）② 反编译质量最高 ③ 200+ 插件生态 ④ 处理器模块覆盖最广 | FLIRT **可以搬**（格式已公开，见 §3.1）；反编译**不能搬**（见 §4.1） |
| **Ghidra** | ① **SLEIGH + P-Code 中间表示**：用约 60 条原子操作覆盖几乎所有架构，架构无关 ② 反编译管线**四阶段**（Cifuentes 1994 论文）③ headless 批量分析 ④ 团队协作 | P-Code 的**思路可以搬**（我们已有 IR 雏形）；完整反编译管线**工作量巨大** |
| **Binary Ninja** | ① **BNIL 多层 IR**（LLIL/MLIL/HLIL），用途分层清晰 ② API 设计最好，自动化最舒服 | 分层 IR 的**分层思想可以搬** |
| **radare2 / Rizin** | ① 纯 CLI + 管道，Unix 哲学 ② 脚本化能力最强 ③ 架构覆盖极广 | CLI 设计理念**已经在用** |

> **一句话总结**：这三家真正的分水岭不是「能不能反汇编」，而是 **① 反编译器的质量 ② 库签名库的规模 ③ 中间表示的分层设计**。
> 前两条我们搬不动（一个要人年，一个要签名数据），**第三条能学**，第四条（FLIRT 格式）**能搬**。

### 2.2 中间表示（IR）—— 三家共同的核心机密

这是最值钱的设计，也是最被低估的：

```
[机器字节]
   ↓ SLEIGH / 各自翻译器
[原始 P-Code / LLIL]           ← 架构无关、寄存器传输级
   ↓ SSA 构造（每变量只赋值一次）
[High P-Code / MLIL]           ← 数据流清晰，死代码可消除
   ↓ 类型传播 + 控制流结构化
[结构化 AST / HLIL]            ← if/while/switch 已还原
   ↓ 代码生成
[C 伪代码]
```

**关键洞察（对我们的启发）**：
- **SSA 是分水岭**。没有 SSA，数据流分析无法做；有了 SSA，死代码消除、常量传播、类型推断才有基础。
- **反编译的核心不是"翻译指令"，是"还原结构"**：把 CFG 用图的可归约性（reducibility）还原成 `if`/`while`/`switch`。
- 我们的 `lib_code.py` 已有基本块/CFG，**下一步该做的是 CFG → 结构化的还原**，这是从"反汇编器"升级到"反编译器"的唯一路径。

### 2.3 二进制差分（补丁比对）

| 工具 | 核心算法 | 可迁移 |
|---|---|---|
| **Google BinDiff** | 多级匹配：哈希匹配 → **素数签名**（助记符→素数，乘积对顺序不敏感）→ **MD Index**（CFG/调用图的拓扑特征）→ 结构匹配 → 松弛匹配 | **全部可搬**，算法已公开（见 §3.2） |
| **Diaphora** | 多启发式 + **伪代码 diff** + **数据类型/结构体移植**（独门） | 启发式可搬，伪代码 diff 依赖反编译器 |
| **Ghidra VT** | Correlator 会话 | 思路可搬 |

**神特点**：不是"能比对两个文件"，而是 **① 用置信度分层，高置信结果当锚点向外传播 ② 素数签名对指令重排免疫 ③ MD Index 对编译器优化免疫**。
这三点都是纯算法，**零依赖可以实现**。我们现有的 `sim` 只有单一指纹比对 —— **这是最大的待升级点**。

### 2.4 混淆对抗（恶意软件分析师日常）

| 技术 | 对抗它的工具 | 算法本质 | 可迁移 |
|---|---|---|---|
| **栈字符串**（逐字节 `mov [rsp+N], imm`） | **FLOSS**（Mandiant） | 沿 CFG **模拟执行**栈写入 | **可以搬**，见 §3.3 |
| **XOR/RC4/AES 编码串** | FLOSS | 识别解密循环 → 模拟 → 尝试解码 | **可以搬**（XOR 优先） |
| **API 哈希**（ROR13 等） | FLOSS / 手工 | 遍历导出表算哈希比对 | **可以搬**，需要导出表（我们已有） |
| **控制流平坦化** | D810、手工 | 识别 dispatcher 状态变量 | 难，先不做 |
| **加壳** | 查壳器 + 脱壳脚本 | 特征匹配 / OEP 定位 | 查壳我们已有 |
| **反调试** | ScyllaHide / TitanHide | 内核驱动对抗 | 只做静态识别（已有） |

### 2.5 AI 辅助逆向（2025–2026 新战场）

| 方向 | 代表 | 现状 | 对我们的意义 |
|---|---|---|---|
| **LLM 反编译修复** | ReF Decompile（SOTA 61.43%） | 端到端 LLM 反编译**尚未超过**传统反编译器，主要用来**修可读性/还原变量名** | 我们的定位应该是**给 LLM 喂结构化事实**，不是自己当 LLM |
| **领域微调模型** | **ReCopilot**（奇安信，7B） | 函数名恢复+变量类型推断**超过通用大模型 13%**，用**数据流+调用图**做上下文增强 | **关键启发**：给模型的上下文质量决定效果 → 我们的 `semantics`/`cfg`/`xref` 输出正是这个上下文 |
| **MCP 桥接** | GhidraMCP / ida-pro-mcp / ReVa | 让模型直接驾驶反编译器 | 我们已探测这层（`doctor.ai_stack`） |
| **安全风险** | arXiv:2605.30667 | **提示注入**：字符串里的对抗指令能骗过 LLM 流水线 | 已在 SKILL.md 写成硬约束 |

> **对我们的定位结论**：我们**不做** LLM，我们做 **「给 LLM 的高质量结构化事实层」**。
> ReCopilot 的实证说明：模型效果 = 模型能力 × **上下文质量**。
> 上下文质量那一半，正是 `triage / semantics / cfg / xref / capability` 该干的活。
> 所以我们的路线不是"更聪明的 AI"，而是 **"更完整的证据 + 更明确的置信度"**。

## 三、可搬运的具体算法（已核实格式，可直接实现）

### 3.1 FLIRT `.pat` 格式规范 ✅ 已完整掌握

```
518B4C240C895C240C8D5C240C508D442408F7D923C18D60F88B43F08904248B 21 B4FE 006E :0000 __EH_prolog3_GS_align ^0041 ___security_cookie
└──────────────────── 32 字节模式 ────────────────────┘ │  │    │   │            └ 引用名
                        重定位处用 .. 通配                   │  │    │   └ 公共名（:偏移 名字）
                                                           │  │    └ 函数总长度（hex）
                                                           │  └ CRC16（模式之后要校验的字节数）
                                                           └ CRC16 覆盖的字节数（hex）
```

| 字段 | 含义 |
|---|---|
| 前 32 字节 | 函数起始字节，最长 32；`..` 表示重定位/可变字节；不足 32 用 `..` 补齐 |
| `alen` | 模式之后参与 CRC16 校验的字节数（hex，最多 255） |
| `crc16` | 期望校验值（hex）；CRC 初值 `0xFFFF`，结果 `(crc>>8) ^ (crc&0xFF)` 位交换 |
| `funklen` | 函数总长度（hex，可选） |
| `:offset name` | 公共符号名及其在函数内偏移 |
| `^offset name` | 引用符号名（跳转到函数外） |
| `(xxxx: yy)` 尾部 | 函数长于 287 字节时的判别字节（tail bytes） |

**匹配流程**：模式通配匹配 → 定位后用 CRC16 校验后续字节 → 比对函数长度 → 回填符号名。
**关键点**：CRC16 是**消除同前导字节误匹配**的核心机制，必须实现。

> 已有开源参考实现：`williballenthin/lancelot`（Rust，支持 .pat 与 .sig）、`mandiant/flare-ida` 的 `idb2pat.py`（生成端，Apache-2.0）。
> **我们的实现策略**：只做 `.pat` 文本格式（人类可读、可自建），不碰二进制 `.sig`（压缩+版本多，收益低）。

### 3.2 BinDiff 多级匹配算法 ✅ 已完整掌握

**函数级匹配（按置信度从高到低）**：

| 算法 | 原理 | 置信度 |
|---|---|---|
| 哈希匹配 | 函数字节哈希（含基本块/指令）相同 | ★★★★★ |
| 名称哈希 | 函数名哈希（导入函数专用，误配率极低） | ★★★★★ |
| **素数签名** | 每条助记符→唯一素数，**基本块素数=指令素数之和，函数素数=基本块素数之和**；乘法/加法可交换 → **对指令重排免疫** | ★★★★ |
| **MD Index** | 拓扑特征向量：入度/出度/前驱后继度/拓扑层级，用 `√2,√3,√5,√7,√11,√13` 加权求和；**自顶向下 + 自底向上双向计算** | ★★★★ |
| 地址序列 | 入口地址顺序 | ★ |
| 调用序列 | 调用点拓扑位置 | ★ |

**相似度计算权重（实证值，直接照搬）**：

```
函数相似度 = 匹配边占比×25% + 匹配基本块占比×15%
           + 匹配指令占比×10% + 流程图 MD Index 差异×50%
```

**关键洞察**：
- **MD Index 占 50% 权重** —— 结构比内容重要得多。
- **锚点传播**：高置信匹配当"固定点"，用它去约束邻居的候选集 → 把 O(n²) 降下来。
- **置信度用 Sigmoid 压缩**，避免个别弱匹配拉偏整体评估。

### 3.3 栈字符串静态恢复 ✅ 算法已明确

**检测特征**：
```asm
mov byte [rsp+00h], 68h    ; 'h'   ← 连续 ≥8 条
mov byte [rsp+01h], 74h    ; 't'      单字节立即数写栈
mov byte [rsp+02h], 74h    ; 't'      目标偏移连续
mov byte [rsp+03h], 70h    ; 'p'
```
**宽字节变体**（更隐蔽）：
```asm
mov dword [rsp+00h], 70747468h   ; "http" (小端)
mov dword [rsp+04h], 2F2F3A68h   ; "h://"
```

**恢复算法**：
1. 在反汇编流里找 `MOV` 且目的操作数是 `[rsp/rbp + 常量]`、源是立即数。
2. 按偏移**排序后拼接**（不是按指令顺序 —— 编译器可能重排）。
3. 遇到 `0x00` 截断，长度 ≥4 且全可打印才输出。
4. 同时支持 1/2/4/8 字节立即数（小端展开）。

**判别阈值（来自实战经验）**：**≥8 条单字节立即数写栈、且偏移落在 64 字节窗口内** —— 这个模式在正常未混淆代码里几乎不出现。
我们手上有 `lib_x86.py` 的 `mem_ref`，**这个特性可以直接实现**。

### 3.4 反编译管线（Cifuentes 1994 四阶段）—— 理论框架

```
① 反汇编与翻译   → IR（架空中立）
② 数据流分析     → SSA（每变量单次赋值）→ 死代码消除、复制传播
③ 控制流分析     → 图可归约性 → 结构化 if/while/switch
④ 代码生成       → 可读 C 伪代码
```

**SSA 与内存别名问题**（Ghidra 切片器同款）：
- 纯寄存器级 SSA **不够** —— 二进制的值在内存里流转，`STORE`→`LOAD` 会断链。
- 补法：**指针基址恢复 + 字段敏感偏移计算**
  - `PTRSUB`: `offset = base + offset_val`
  - `PTRADD`: `offset = base + index × elem_size`
  - 动态偏移 → 退化为保守的 "may-alias"
- **时间可达性校验**：`LOAD` 只能连到 CFG 上真正可达的 `STORE`，否则会追到"未来"的写。

**避坑备忘**
- FLIRT 识别率随编译器变化极大：GCC -O0 约 95%，GCC -O2 静态链接约 75%，Rust 约 50%，TinyCC 约 40%。
  → 输出**必须带置信度**，不能把 FLIRT 命中当成"确定"。
- 反编译器结果「80% 对 20% 错」，典型失效：栈指针追踪丢失、寄存器活跃性误判、函数边界错误。
  → 任何反编译结论都要能回汇编复核。
- 编译器优化（内联、循环展开、peephole）是差分噪声的主要来源；**故意**用基因算法搜优化参数可以让两个等价二进制在结构上完全不同。
  → 差分结果要允许"结构不相似但语义相同"。
