### 本轮修复：PE ExportOrdinalTable 语义错误（本项目至今最严重的解析 bug）

`lib_formats.parse_pe` 把 `ExportOrdinalTable` 的值当成最终 ordinal，
而 PE 规范规定它是 **EAT 的索引**（最终 ordinal = `ordinal_base + 索引`）。
旧实现拿该值直接查以 `ordinal_base + i` 为键的字典，**只要 `ordinal_base != 0`
就全部落空**。

实测对比：

| 样本 | ordinal_base | 修复前 rva 命中 | 修复后 |
|---|---:|---:|---:|
| user32.dll | **1502** | **0 / 1050** | **1050 / 1050** |
| kernel32.dll | 1 | 1697 / 1698 | 1698 / 1698 |
| ntdll.dll | 1 | — | 2522 / 2522 |

函数命名率 user32：**0.5% → 40.2%**（8 → 1026 个函数）。

**为什么藏了这么久**：kernel32 恰好 `ordinal_base=1`，掩盖了缺陷 ——
这是"幸存的样本掩盖缺陷"的典型。教训：解析器必须用**多个形态差异大的样本**
验证，不能只测一个"看起来正常"的。

## 与顶级工具的定位差异（诚实声明）

我们**不是** Ghidra/IDA 的替代品，也不该是。差别在形态：

| | Ghidra / IDA | 本项目 |
|---|---|---|
| 形态 | GUI 交互、逐函数人工分析 | CLI + AI 编排、批量、可组合 |
| 上限 | 专家级（有伪代码） | 事实层强 + 编排强 |
| 适合 | 深度单文件逆向 | 大批量初筛 / CI 集成 / Agent 事实层 |

**顶级工程师不会用我们替代 Ghidra**，但会用我们做「第一遍事实采集」——
这一步目前占他们 60% 的时间。

## 距离结论（诚实估算）

| 维度 | 达成度 | 说明 |
|---|---:|---|
| 事实采集自动化 | **~85%** | A 档齐备，命名率还能提 |
| 行为理解 | **~35%** | 规则库 20 vs 3600，标签覆盖 37% |
| 伪代码级理解 | **0%** | C 档空缺 |
| 硬件/固件覆盖 | **~20%** | 无 MIPS/RISC-V，无 SquashFS 取内容 |
| 应用生态接口 | **~45%** | 有静态抽取，缺 DEX 方法级调用图 |

**综合：约 40%。**

从"能用的 AI 事实层工具"到"顶级逆向能力"，差的**不是数量，是那 60%**——
而这 60% 集中在 C 档（伪代码 / 类型 / 数据流）和硬件架构覆盖两处。

## 建议的推进顺序（按投入产出比）

1. **规则库扩容**（20 → 数百条）：低风险、高收益，直接把行为理解从 35% 拉到 60%+
2. **DEX 方法级接口地图**：正好命中"APK 传电脑就看出调什么接口"的用户场景
3. **IR + 控制流结构化（伪代码雏形）**：C 档第一块砖，也是反混淆的地基
4. **MIPS / RISC-V 解码器**：硬件覆盖从 20% 起步
5. **类型恢复 / def-use**：最难，但决定能不能啃私有协议

前三项做完，综合可达 **约 60–65%**；五项全做完才谈得上"接近专家"。
